## Technical
- Engine: custom (BEC). Data files are Yay0-compressed (a standard Nintendo compression format), 5152 of them, packed from ROM offset `0x1BB280` to about `0xEC0000`. Everything before `0x1BB280` is program code and data tables. Used data ends at `0x1C31B40`; the last ~3.8 MB of the ROM is empty (`FF`).
- Where the text lives (all confirmed by decoding, 2026-10-03):
  1. **Font-drawn text** (dialogue/briefing lines): strings of 16-bit character codes in the program data area, seen at `0x112264`-`0x1133A0` and `0x1909CD`-`0x191C3E`. `0x0000` = end of string, `0x0001` = line break, `0x0010` = space. Strings are padded to 4 bytes. Code points at them with pointers (about 195 pointer bytes changed in the Korean patch, range `0xED033`-`0x192793`).
  2. **Font**: 538 glyphs, each 24x24 pixels, 4 bits per pixel, each its own Yay0 file from `0x1BB280` to `0x1D9000`. Glyph table at `0x3FD90`: 12 bytes per glyph = (offset from `0x1BB280`, compressed size, unpacked size `0x120`). Compressed size 0 means "stored raw" (the Korean patch uses this). Per-glyph width table at about `0x3EAAC` (one byte each), so the game already supports variable-width letters.
  3. **Text baked into images**: image files have a 16-byte header (width u16, height u16, flags u32, 8-letter ASCII name) then 4bpp or 8bpp pixels. The Korean patch changed about 160 images (names like `MMVNAM##`, `M##INST#`, `M##GIN##`, `D##EDA##`, `D##TITLE`, `DENDSR##`): Angel names, title cards, mission instructions, result screens, credits, menus.
- Encoding: **custom table, not Shift-JIS.** Character code = glyph number in the game's own font + `0x10` (glyph 0 is the blank, so `0x0010` is a space). Confirmed on `00F6 001E 00C1 0108 0065 005F 005C 0079` = 第3使徒サキエル, and on all 229 extracted strings reading as sensible Japanese. The table is `scripts\charmap_jp.txt`, read by eye from the font sheet; a misread rare kanji is possible, so treat odd-looking kanji with suspicion.
- Text blocks: `0x112220`-`0x112DA0` (missions up to Jet Alone) and `0x190950`-`0x191C64` (Jet Alone onward). Strings start on 4-byte boundaries. Block 1 ends with a Jet Alone intro that the Korean patch left untouched and block 2 repeats, so it may be unused. Other data (colour palettes) sits between strings in block 1.
- Tools used:
  - xdelta3 3.1.0 (`tools\xdelta3\`), from github.com/jmacd/xdelta-gpl releases. Applies/creates `.xdelta` patches. Fails on non-ASCII filenames: copy patches to ASCII names first.
  - Own tools in `tools\eva64\` (Python 3.11, standard library only): `eva64lib.py` (Yay0 decompressor, image and font decoding), `extract.py`, `extract.bat`.
- How to extract (exact steps): run `tools\eva64\extract.bat`. It checks the ROM hash, then writes `work\extract\text\strings_jp.tsv`, `work\extract\font\`, `work\extract\images\all\` (every image as greyscale PNG), `work\extract\images\index.tsv` and `work\extract\images\changed_by_korean\` (JP and KR versions side by side). The Korean comparison needs `work\korean\eva_k_1.z64` (Korean patch applied to a ROM copy with xdelta3).
- How to reinsert and build (exact steps): `tools\eva64\build.bat` with no arguments rebuilds unchanged and reports whether the result is byte-identical. `tools\eva64\build.bat scripts\<changes>.tsv <name>` applies a changes file (columns: string id, new text) and writes `work\build\<name>.z64`. It repacks strings, rewrites every pointer to a moved string, and recalculates the header checksum (bytes `0x10`-`0x17`, CIC-6102 method, confirmed to reproduce the original value). Images and font cannot be reinserted yet (needs a Yay0 compressor or raw storage).
- Pointers: memory address = `0x80000000` + ROM offset - delta. Delta is `0xA9510` for text block 1 and `0x14FA40` for block 2. Strings are referenced either by a 4-byte address in a table or by a MIPS `lui`+`addiu` instruction pair. 254 references found for 218 strings; they include 203 of the 205 pointer words the Korean patch changed (the other two, at `0x1743E4`/`0x1743E8`, are not string pointers by this mapping). 11 strings have no reference found (ids 0001-0003, 0031, 0032, 0065, 0066, 0082-0084, 0227); the builder keeps those at their original position, so they cannot grow.
- Space: strings are packed back to back with no slack. Solution built 2026-10-05 (test 6, not yet confirmed in-game): the **text pool**. The overlay loader (ROM `0x162C0`) reads the table entry, copies `romEnd - romStart` bytes from ROM to `ramStart`, then clears the bss range. So `build.py` writes an enlarged copy of the overlay into empty ROM space at `0x1C40000` (original bytes, zeros where bss sits, then the new strings), and changes the table entry's rom start/end and ram end. Pool strings sit in memory straight after the overlay's bss (`0x8006C5A0` for ovl3, `0x80052250` for ovl7), below `0x80084DD0` where the largest overlay ends. A changed string that still fits its old slot is written in place; a longer one goes to the pool and its pointers are rewritten; an unreferenced one must fit in place. For ovl3 the pool must stay below `0x80078000` so the `lui` half of code references does not change (the build stops if it would).
- Image reinsertion (built 2026-10-05, test 7, not yet confirmed in-game): `build.bat ... en` inserts every `work\images_en\<file number>_<name>.png` over the original image file, in place. The new image must compress to no more than the original's space (the gap to the next file), otherwise the build stops; there is no relocation for images yet. Text-only images are generated by `tools\eva64\makeimages.bat` from `scripts\images_en.tsv` (file, name, text, size, weight, width%, align, x, baseline). Images that contain game artwork must be edited by hand and kept in `work\` only (rule 8). The Yay0 compressor is slow pure Python, fine for small images, untested on the 320x240 ones.
- Briefing labels are images `0875 D01SXT00` (作戦内容), `0876 D01SXT01` (使用EVA), `0877 D01SXT02` (攻撃目標): 96x24, 4-bit, plain white letters with no outline. Found by searching all images for the font's kanji shapes. Strings 0001-0003 are not shown on that screen.
- `tools\eva64\verify.bat <name> [en]` simulates the loader on a built ROM, follows all 252 pointers, prints each changed string with per-line pixel widths, and flags lines over 288 px.
- **Automated screenshots (harness), working since 2026-10-05:** `tools\eva64\harness.bat <rom name> <plan>` runs a build (or `original`) in BizHawk 2.11.1 (`tools\bizhawk\`) under a generated Lua script at high speed, presses buttons per `tools\eva64\plans\<plan>.txt` (steps: `wait N`, `press Button N`, `shot name`, `record frames interval name`), saves screenshots to `work\harness\<rom name>\` and builds contact sheets in its `sheets\` folder for Claude to read. Must use BizHawk's **Ares64** core: the default Mupen64Plus core shows a black screen on modified ROMs (the harness sets this in its own config, `work\harness\bizhawk_config.ini`). Plan `mission1` goes power-on -> Start -> A x3 and records through the mission 1 intro to the briefing screen (about 7,200 frames). The BizHawk window appears on the desktop while it runs. Not built yet: logging which string is drawn, reaching later missions (needs save states, a completed save, or memory pokes).
- **Scene number:** the 16-bit value at memory `0x800D5114` (RAM offset `0D5114`) is the game's current scene. Writing a new value there makes the game switch to that scene (the setter function at ROM `0x163CC` does nothing more than store it). ## Limits
- Characters per line: measured in pixels, not characters. Narration lines are centred and clipped at about 288 pixels wide (seen in-game: a 407-pixel test line lost both ends). Line width = sum of the width-table values of its characters. Original Latin capitals are 18-22 pixels wide, digits 12-17, space 12; the widest original single-line string is 326 pixels (on a different screen, limit there not measured).

- Letter spacing (found 2026-10-03 by disassembly with capstone): the main program is loaded so that memory address = `0x80095400` + ROM offset. Text routines: measure one line `0x800A7464` (ROM `0x12064`), measure multi-line `0x800A74A8` (`0x120A8`), draw wrapper `0x800A7660` (`0x12260`, args: string, letter spacing, line spacing, mode), draw `0x800A77D8` (`0x123D8`). Each caller passes a signed letter-spacing value added after every character: -2 in narration (some -3), about -5 on the briefing screen. There is no horizontal scaling. `build.bat ... en` patches three instructions (`0x12078`, `0x120C0`, `0x12308`) so spacing is always 0 and the width table alone decides. The draw wrapper allocates its texture as 24 pixels per character of the longest line, so very long lines cost memory (not yet a problem at 34 characters).
- **Correction 2026-10-05:** the first spacing patch (test 4) zeroed the spacing in the draw wrapper at `0x12308`, which also changed the texture size; callers compute that size themselves, so all text came out as garbage. Current patch set is `0x12078`, `0x120C0` (measuring) and `0x12558` (pen step inside draw only); texture size is left alone. Built as test 5, not yet confirmed in-game.
- Decomp project (github.com/farisawan-2000/evangelion, cloned to `tools\evangelion-decomp`, WIP, no licence file): all overlays load at `0x80025C00`. ovl3 = ROM `0xCF110`-`0x113B10` (text block 1), ovl7 = ROM `0x175640`-`0x1A1880` (text block 2). Overlay table `gOverlayTable` at `0x800D4F50` (ROM `0x3FB50`), 0x28 bytes per entry: rom start/end, ram start/end, text, data, bss ranges. The pointer scan in `build.py` is now limited to these overlay ranges (the old wider scan had two false hits in ovl6).
- ovl7 text table (from the decomp's `notes\ovl7_textparms.txt`, by IlDucci), at ovl7 start + `0x1C624`, 20 bytes per entry: string pointer, X, Y, minimum texture height, minimum texture width, mission number, scene number, letter spacing (signed), 0, alignment (2 = left, 3 = centred), style (1 = faded subtitle, 2 = dialogue, 3 = no outline), 2 zero bytes. So for block 2 position, alignment and spacing are data, not code.
- Character table cross-check: the decomp's `tools\charmap.py` agrees with `charmap_jp.txt` on 525 of 538 glyphs. Of the 13 differences, 7 are naming only, 5 are their misreads by context (姿, 回, ゼ, 廃/墟, 然), and 1 was mine: glyph 497 is hiragana べ, now fixed.
- Test 3 in-game result (before the spacing patch): font readable, narration centred and fitting; briefing text crushed together with no visible spaces; untranslated lines scrambled as expected.
- Text position: not always centred. In test 2 the first narration line looked centred but a later replaced line (`TEST 3`) sat left of centre, so at least some lines have a fixed start position set in code. Not yet located.
- Glyph pixel values: 0 = see-through, 1 = dark outline, 2-15 = brightness. In the original font some complex kanji are stored raw (table size 0) instead of Yay0.
- English font: Noto Serif (SIL Open Font License, `tools\fonts\`), 18 px, weight 650, width 62.5%, made by `tools\eva64\makefont.bat` into `work\font\font_en.json` and `scripts\charmap_en.txt`. Slots: 1 `,` 2 `.` 4 `:` 5 `?` 6 `!`, 11-20 digits, 21-46 A-Z, 47-72 a-z, 73-80 `' " - ; ( ) / &`, space width 5. Average lowercase letter 9.5 px, so about 34 characters fit in 288 px. Build with `build.bat <changes> <name> en`; it repacks the whole font area (116,008 of 122,240 bytes used with 76 slots replaced).
- Font notes: 538 glyph slots, 24x24, variable width via width table. English needs ~2-3x as many characters as Japanese and each costs 2 bytes, so strings will grow and must be relocated.

## Style overrides
**Approved by the user 2026-10-05.** Anything that differs from `docs\STYLE_GUIDE.md` for this game.
- Official names win: terms follow the long-standing official English releases of the TV series (ADV-era wording), which is what most English-speaking fans know.
- Name order: **Western** for this game (Shinji Ikari, Kaworu Nagisa), because the official English releases use it. Differs from the style guide default.
